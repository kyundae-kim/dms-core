# 소프트웨어 요구사항 정의서

## 1. 목적 및 적용 범위

본 문서는 문서 관리 공통 구성요소가 충족해야 하는 소프트웨어 요구사항을 정의한다. 본 제품은 다른 업무 시스템에 통합되어 사용하는 Python SDK이며 독립 실행형 API 서버가 아니다.

제품은 호출자가 이미 생성한 저장소 연결 또는 문서 정보 저장소·문서 본문 저장소의 공개 구성요소를 주입받아 문서 작업을 수행해야 한다. 제품은 환경변수에서 인프라 연결을 읽거나 저장소 client를 생성하는 구성 경계를 제공하지 않아야 한다.
모든 일반 문서 작업은 호스트가 제공하는 개인 또는 그룹 문서 파티션 안에서 수행되어야 한다. 제품은 문서 정보, 문서 본문, 등록 작업, 목록 커서, 삭제 및 복구를 정확한 파티션으로 격리해야 한다. 인증과 그룹 소속 확인은 호스트가 수행하며, 제품은 호스트가 제공한 접근 정책을 선택적으로 문서 작업에 적용해야 한다.

## 2. 용어

- 문서 본문: 파일의 실제 바이트 데이터와 관련 속성이다.
- 문서 정보: 문서 식별자, 원본 파일명, 콘텐츠 유형, 크기, 저장 위치, 상태, 생성·수정 시각 및 부가 정보이다.
- 호출자 부가 정보: 호출자가 문서와 함께 보존하기 위해 제공하는 JSON 객체이다. DMS는 키·값의 업무적 의미나 특정 업무 스키마를 정의하지 않으며, JSON 객체를 문서 정보에 보존한다.
- 논리 삭제: 문서 정보를 보존한 채 문서를 삭제된 상태로 표시하는 처리이다.
- 완전 삭제: 문서 본문과 문서 정보를 모두 제거하는 처리이다.
- DMS 관리 데이터: DMS가 관리하는 문서 정보, `documents/` prefix 아래의 문서 본문 및 설정된 업로드 작업 기록이다.
- 데이터 적재 초기화: 기존 DMS 관리 데이터를 비우고 새로운 데이터 묶음을 적재할 수 있는 빈 상태를 만드는 관리 작업이다.
- 불일치 상태: 문서 본문과 문서 정보의 존재 여부 또는 문서 상태가 서로 맞지 않는 상태이다.
- 커서 페이지네이션: 정렬 기준상의 마지막 위치를 불투명한 값으로 전달하여 다음 결과 묶음을 조회하는 방식이다.
- 종료 보장 반복자: 전체 소비와 읽기 실패 때 자동으로 자원을 정리하고, 일부 소비 후에는 명시적인 종료를 통해 즉시 정리할 수 있는 반복자이다.
- 비동기 공개 경계: 동기 공개 작업과 동일한 결과·오류·정합성 계약을 비동기 호출 방식으로 제공하는 경계이다.
- 공개 데이터 전송 모델: 호스트 시스템이 내부 저장소 모델을 다시 선언하지 않고 직렬화와 스키마 생성에 사용할 수 있는 공식 공개 결과 형식이다.
- 호출자 소유 자원: 호출자가 생성·관리하며 SDK가 종료하지 않는 저장소 구성요소와 연결 자원이다.
- SDK 생성 스트림: 문서 처리 중 SDK가 직접 열어 반환하며 사용 종료 시 SDK가 닫아야 하는 파일 또는 본문 스트림이다.
- 문서 파티션: 한 문서와 관련 작업이 속하는 단일 관리 범위이다. 종류와 식별값의 조합으로 식별하며 개인 또는 그룹 중 하나여야 한다.
- 개인 파티션: 호스트가 관리하는 사용자 식별값으로 구분하는 문서 파티션이다.
- 그룹 파티션: 호스트가 관리하는 그룹 식별값으로 구분하는 문서 파티션이다.
- 신뢰 파티션: 호스트가 인증, 그룹 소속 및 파티션 선택 권한을 확인한 뒤 제품에 전달한 문서 파티션이다. 제품은 전달값을 데이터 관리 범위로 사용하고, 별도의 호스트 제공 접근 정책이 있으면 문서 작업 권한을 추가로 판단한다.
- 접근 맥락: 호스트가 인증한 호출자의 주체, 그룹 및 역할 정보를 호출 단위로 전달하는 불변 값이다. 제품은 값을 해석하거나 인증하지 않는다.
- 접근 정책: 접근 맥락과 문서 작업 종류 및 공개 문서 정보를 바탕으로 작업 허용 여부를 결정하는 호스트 제공 규칙이다. 제품은 정책을 호출하고 거부 결과를 문서 작업에 적용한다.
- 접근 정책 판정 대상: 특정 문서가 없는 작업에서는 null이고, 특정 문서 작업에서는 내부 저장 위치를 제외한 공개 문서 정보이다.
- 작업 관찰자: 문서 작업의 완료 또는 실패 정보를 로깅·감사·측정 체계로 전달하는 선택적 호스트 제공 경계이다.



## 3. 기능 요구사항

### 3.1 조립 및 소유권 경계

- SRS-CFG-001: 제품은 완성된 문서 정보 저장소와 문서 본문 저장소 구성요소를 주입하는 component 기반 조립을 제공해야 하며, 환경변수에서 저장소 client를 생성하거나 읽지 않아야 한다.
- SRS-CFG-002: component 기반 조립은 문서 정보 저장소와 문서 본문 저장소를 필수로 받고, 업로드 작업 저장소는 선택적으로 받을 수 있어야 한다. 업로드 작업 저장소가 없으면 영속 멱등성 작업을 요구하는 기능은 구분 가능한 유효성 오류를 제공해야 한다.
- SRS-CFG-003: 제품은 최대 파일 크기, 로거, 복구 감사 경계, 작업 관찰자 및 호스트 제공 접근 정책을 포함하는 공통 조립 정책을 적용할 수 있어야 한다. 양수여야 하는 정책 값은 조립 전에 검증해야 하며, 저장소 readiness 확인과 client lifecycle은 조립 정책에 포함하지 않아야 한다. 접근 정책이 없으면 기존 신뢰 파티션 동작을 유지하고, 접근 정책이 있으면 해당 정책을 문서 작업에 적용해야 한다.
- SRS-CFG-004: 제품은 주입된 MinIO client와 bucket 이름으로 SDK를 조립할 때 지정 bucket의 존재를 확인하고, 없으면 생성해야 한다. bucket 생성 이후에도 MinIO client 및 bucket의 종료·삭제 lifecycle은 호출자가 소유해야 한다.
- SRS-CFG-005: 동기 조립 경계는 동기 SQLAlchemy 연결과 동기 MinIO client를 사용해야 하며, 비동기 조립 경계는 비동기 SQLAlchemy 연결과 비동기 저장소 adapter를 사용해야 한다. 비동기 조립 경계에 주입된 동기 MinIO client의 blocking 호출은 event loop 밖에서 실행해야 한다. 각 조립 경계는 다른 경계의 blocking 저장소 호출을 event loop에서 암묵적으로 재사용해서는 안 되며, 주입된 client와 bucket의 lifecycle은 호출자 소유로 남겨야 한다.

### 3.2 접근 제어

- SRS-ACC-001: 제품은 사용자 인증, 사용자 식별자 발급 및 그룹 구성원 확인을 수행하지 않아야 하며, 호스트가 인증·구성원 확인 후 제공한 `AccessContext`를 신뢰하여 사용해야 한다.
- SRS-ACC-002: `AccessContext`는 호출 단위로 제공되는 불변 공개 모델이어야 하며, 주체·사용자·그룹·역할 값은 호스트가 해석하는 비어 있지 않은 불투명 문자열이어야 한다. 제품은 해당 값의 의미나 소속 관계를 고정하거나 재검증하지 않아야 한다.
- SRS-ACC-003: 제품은 조립 시 선택적으로 호스트 제공 `DocumentAccessPolicy`를 받아야 하며, 정책 판정에 작업 종류, 호출 맥락 및 공개 문서 정보를 제공해야 한다. 특정 문서가 없는 등록·목록·업로드 작업 상태·데이터 삭제 작업의 문서 정보는 null이어야 하며, 특정 문서 작업의 판정 대상은 내부 저장 위치를 제외한 공개 문서 정보여야 한다.
- SRS-ACC-004: 접근 정책이 허용하지 않는 작업은 `AccessDeniedError`로 구분해야 하며, 오류의 `code`는 `access_denied`, 상위 분류는 `authorization`, 재시도 가능 여부는 false여야 한다. 정책 판정 중 발생한 호스트 오류의 상세 내용은 공개 오류 메시지에 노출하지 않아야 한다.
- SRS-ACC-005: 접근 정책은 문서 등록·파일 등록·스트림 등록, 공개·관리 문서 정보 조회, 목록·전체 순회, 본문·본문 스트림·복사, 논리·완전 삭제, 업로드 작업 상태 조회, 상태 점검·복구 및 전체·파티션별 데이터 삭제·적재 초기화에 일관되게 적용되어야 한다. 정책이 거부한 작업은 문서 본문, 문서 정보, 업로드 작업 기록 또는 대상 출력에 대한 변경을 수행하지 않아야 한다.
- SRS-ACC-006: 일반 공개 목록과 복구 대상 목록은 정책 판정을 저장소 조회 및 페이지 제한보다 먼저 수행해야 하며, 정책 적용을 위해 결과 페이지를 만든 뒤 항목을 제거하는 방식으로 권한 경계를 우회해서는 안 된다. 파티션 격리·커서 조건·목록 순서의 의미도 유지해야 한다.
- SRS-ACC-007: 내부 저장 위치를 포함하는 관리·복구 조회와 상태 점검·복구, 논리·완전 삭제, 파티션별·전체 데이터 삭제 및 적재 초기화는 일반 문서 읽기·쓰기 권한과 구분되는 작업 종류로 정책에 전달되어야 한다.
- SRS-ACC-008: 동기 공개 경계와 비동기 공개 경계는 동일한 접근 정책 입력, 허용·거부 의미 및 `AccessDeniedError` 계약을 적용해야 한다. native async 경계에서 동기 정책 callback을 사용할 경우 callback 실행이 event loop를 직접 차단하지 않아야 하며, 비동기 정책 callback은 await되어야 한다.
- SRS-ACC-009: 접근 정책이 제공되지 않은 조립은 기존 신뢰 파티션 계약과 호환되어야 한다. 다만 호스트는 외부 호출자가 SDK를 직접 사용할 수 있는 배포 경계에서 접근 정책을 제공해야 하며, 제품은 정책 미제공을 인증 완료로 간주하지 않아야 한다.
- SRS-ACC-010: 제품은 사용자·그룹·구성원 정보 또는 접근 정책 규칙의 저장·변경 API를 제공하지 않아야 한다. 해당 정보의 저장, 구성원 관계의 변경 및 정책 판정 규칙의 소유권은 호스트에 있어야 한다.

### 3.3 문서 등록

- SRS-UPL-001: 제품은 문서 본문, 파일명, 콘텐츠 유형, 선택적 문서 식별자, 호출자 부가 정보 및 작성자 정보를 받아 문서를 등록해야 한다. 호출자 부가 정보는 제품이 관리하는 입력과 구분하여 문서 정보에 보존해야 한다.
- SRS-UPL-002: 제품은 메모리의 바이트 데이터와 정확한 양수 크기가 선언된 동기 바이너리 스트림을 통한 등록을 지원해야 한다.
- SRS-UPL-003: 스트림 등록 시 실제 읽은 크기가 선언된 크기와 일치하는지 검증해야 한다.
- SRS-UPL-004: 제품은 업로드 과정에서 등록 본문의 SHA-256을 계산해야 하며, 파일 및 스트림 등록의 문서 정보에 계산된 체크섬을 보존해야 한다. 바이트 등록은 요청에 제공된 선택적 체크섬을 등록 결과에 반영할 수 있어야 한다.
- SRS-UPL-005: 제품은 빈 본문, 유효하지 않은 파일명·콘텐츠 유형·문서 식별자·작성자·크기 또는 스트림을 저장 전에 거부해야 한다. 호출자 부가 정보는 JSON 객체 또는 null이어야 하며, DMS는 그 업무적 의미나 특정 업무 스키마를 해석하거나 검증하지 않아야 한다.
- SRS-UPL-006: 최대 파일 크기 제한이 설정된 경우 바이트, 파일 및 스트림 등록에 동일하게 적용하고, 제한 초과는 `PayloadTooLargeError`로 구분해야 한다.
- SRS-UPL-007: 제품은 중복 문서 식별자로 등록하려는 요청을 구분 가능한 `DuplicateDocumentError`로 처리해야 한다.
- SRS-UPL-008: 본문 저장 후 문서 정보 저장에 실패하면 저장된 본문을 정리해야 한다. 본문 정리에도 실패하면 불일치 상태를 나타내는 `ConsistencyError`를 제공해야 한다.
- SRS-UPL-009: 바이트 등록에 멱등성 키가 제공되면 동일한 범위와 동일한 DMS 관리 업로드 요청에 대한 완료 결과를 재사용하고, 진행 중인 요청은 재시도 가능한 상태로 구분해야 한다. 호출자 부가 정보는 멱등성 fingerprint 계산이나 비교를 위해 직렬화하지 않아야 한다.
- SRS-UPL-010: 바이트 등록 요청에서 멱등성 키를 사용하려면 비어 있지 않은 멱등성 범위와 영속적인 업로드 작업 저장소를 함께 제공해야 하며, 조건을 충족하지 못한 요청은 저장 작업 전에 유효성 오류로 거부해야 한다.
- SRS-UPL-011: 제품은 바이트 데이터, 파일 경로 및 정확한 양수 크기가 선언된 동기 바이너리 스트림의 세 입력 범주를 지원해야 한다.
- SRS-UPL-012: 스트림 등록은 실제 읽은 크기가 선언 크기와 다르면 문서 정보를 저장하지 않고 업로드된 본문을 정리해야 하며, 호출자가 제공한 스트림을 닫지 않아야 한다.
- SRS-UPL-013: 세 등록 범주는 파일명, 콘텐츠 유형, 문서 식별자 및 작성자처럼 DMS가 관리하는 공통 입력에 동일한 정규화와 검증 규칙을 적용하고 저장 작업 전에 동일한 유효성 오류로 거부해야 한다. 호출자 부가 정보는 등록 경로와 관계없이 해석·정규화·검증하지 않고 문서 정보에 연결하여 보존해야 한다.
- SRS-UPL-014: 크기를 알 수 없는 입력 스트림과 비동기 입력 스트림은 등록 입력으로 지원하지 않아야 한다.
- SRS-UPL-015: 스트림 등록 요청은 요청별 최대 크기, 읽기 단위 조절, 호출자 제공 체크섬 또는 멱등성 값을 받지 않아야 하며, 제품 최대 파일 크기는 모든 등록 범주에 공통으로 적용해야 한다.
- SRS-UPL-016: 제품은 파일 경로를 받아 문서를 등록하는 고수준 경로를 제공해야 하며 파일 열기와 닫기, 실제 크기 확인, SHA-256 계산 및 콘텐츠 유형 추론을 소유해야 한다.
- SRS-UPL-017: 파일 경로 등록은 파일명, 콘텐츠 유형, 문서 식별자 및 작성자에 기존 등록 경로와 동일한 정규화, 검증, 중복 및 부분 실패 계약을 적용해야 한다. 호출자 부가 정보는 기존 등록 경로와 동일하게 해석·정규화·검증하지 않고 보존해야 한다.
- SRS-UPL-018: 파일 경로 등록에서 자동으로 결정한 파일명, 크기, 체크섬 및 콘텐츠 유형은 등록 결과를 통해 호출자가 확인할 수 있어야 하며, 공개 결과에는 내부 저장 위치가 포함되지 않아야 한다.
- SRS-UPL-019: 문서 식별자가 생략되면 제품은 문서 정보 저장소가 발급하는 데이터베이스 자동 증가 식별자를 사용하여 등록하고, 발급된 식별자를 등록 결과에 반환해야 한다. 제품은 별도의 문서 식별자 생성기 주입을 요구하지 않아야 한다.
- SRS-UPL-020: 바이트·파일·크기 확인 동기 스트림 등록은 개인 또는 그룹 문서 파티션을 필수로 받아야 한다. 제품은 같은 파티션을 문서 정보와 본문 저장 namespace에 적용해야 하며, 등록 요청 본문에 별도의 파티션 또는 사용자 식별값을 중복하여 받지 않아야 한다.
- SRS-UPL-021: 멱등성 등록의 작업 범위와 fingerprint는 문서 파티션의 종류와 식별값에 결합되어야 한다. 서로 다른 파티션이 같은 멱등성 범위와 키를 사용해도 각 파티션의 완료 결과를 독립적으로 보존하고, 재생 결과는 동일한 파티션 안에서만 재사용해야 한다.

### 3.4 문서 조회 및 본문 전달

- SRS-GET-001: 제품은 문서 식별자로 삭제되지 않은 문서 정보를 조회해야 하며, 논리 삭제 또는 삭제 진행 상태인 문서는 일반 공개 조회에서 문서 없음으로 처리해야 한다.
- SRS-GET-002: 제품은 문서 식별자로 문서 본문을 조회해야 하며, 메모리 반환과 스트림 반환을 지원해야 한다.
- SRS-GET-003: 동기 문서 본문 스트림은 반복 단위로 읽을 수 있고, 사용 종료 시 관련 자원을 해제할 수 있어야 한다.
- SRS-GET-004: 제품은 문서 상태를 기준으로 문서 정보를 목록 조회할 수 있어야 하며, 일반 공개 목록은 삭제 완료 및 삭제 진행 상태의 문서를 제외해야 한다. 일반 공개 목록은 커서 방식만 허용하고 오프셋 입력을 허용하지 않아야 한다.
- SRS-GET-005: 존재하지 않는 문서 정보 조회는 `DocumentNotFoundError`로 처리해야 한다.
- SRS-GET-006: 문서 정보는 존재하나 본문을 읽을 수 없으면 `ConsistencyError`로 처리해야 한다.
- SRS-GET-007: 기본 공개 목록은 생성 시각과 문서 식별자의 내림차순 복합 순서를 사용해야 한다. 불투명 커서는 상태 필터와 페이지 크기에 결합되어야 하며 결과는 항목, 다음 커서 및 추가 결과 여부를 포함해야 한다. 첫 조회는 커서 없이 시작하고 마지막 페이지의 다음 커서는 없어야 한다.
- SRS-GET-008: 제품은 정확한 멱등성 범위와 키로 업로드 작업의 구조화된 상태를 조회해야 하며, 작업이 없으면 `UploadOperationNotFoundError`를 제공해야 한다.
- SRS-GET-009: 일반 등록 결과, 문서 정보 조회 및 목록 결과는 내부 저장 위치를 포함하지 않는 공개용 문서 정보를 기본으로 반환해야 한다.
- SRS-GET-010: 내부 저장 위치를 포함하는 문서 정보 접근은 복구·관리 용도의 명시적 접근 경로로 분리해야 한다.
- SRS-GET-011: 논리 삭제 또는 삭제 진행 상태인 문서의 본문 및 본문 스트림 조회는 저장소 불일치가 아닌 `DocumentDeletedError`로 거부해야 하며, 삭제 상태 확인은 명시적 관리·복구 조회에서만 허용해야 한다.
- SRS-GET-012: 일반 공개 단건 조회와 커서 목록 조회는 삭제 문서 은닉 정책을 일관되게 적용해야 하며, 호출자가 일반 조회의 상태 조건으로 삭제 완료·삭제 진행 문서를 노출하거나 오프셋 경로를 사용하여 정책을 우회할 수 없어야 한다.
- SRS-GET-013: 제품은 문서 본문을 비동기 반복 가능한 스트림으로 조회하는 인터페이스를 제공해야 하며, 전체 본문을 메모리에 적재하도록 강제하지 않아야 한다.
- SRS-GET-014: 비동기 문서 본문 스트림은 비동기 컨텍스트 관리와 명시적 비동기 종료를 지원하고, 정상 종료·예외·취소·일부 읽기 후 종료에서 관련 자원을 해제해야 한다.
- SRS-GET-015: 커서 페이지 크기는 1 이상 1000 이하로 제한해야 하며, 변조되었거나 현재 조회 조건과 일치하지 않는 커서는 구분 가능한 유효성 오류로 거부해야 한다.
- SRS-GET-016: 동기 문서 본문 스트림은 전체 소비 완료와 읽기 오류에서 소유 자원을 자동으로 정리하는 종료 보장 반복 경로를 제공해야 한다. 일부 소비 후 조기 종료를 위해 반복 호출에 안전한 명시적 종료를 지원하고, 정리 실패가 최초 읽기 오류를 가리지 않아야 한다.
- SRS-GET-017: 비동기 문서 본문 스트림은 전체 소비 완료, 읽기 오류 및 소비 작업 취소에서 소유 자원을 비동기적으로 정리하는 종료 보장 반복 경로를 제공해야 한다. 일부 소비 후 조기 종료를 위해 반복 호출에 안전한 명시적 비동기 종료를 지원해야 한다.
- SRS-GET-018: 종료 보장 반복 경로는 호스트 프레임워크가 문서 본문 스트림 객체의 컨텍스트 관리자에 직접 진입하지 않고 반환된 반복자만 소비하는 경우에도 적용할 수 있어야 한다. 전송 계층의 조기 중단은 반복자의 명시적 종료를 통해 즉시 정리할 수 있어야 한다.
- SRS-GET-019: 제품은 호출자가 커서를 직접 관리하지 않고 문서 전체를 순회하는 동기 및 비동기 반복 경계를 제공해야 하며, 최초 페이지의 상태 필터와 페이지 크기를 모든 후속 페이지에 유지해야 한다.
- SRS-GET-020: 제품은 호출자가 커서를 직접 관리하지 않고 복구 대상을 제한된 묶음으로 순회하는 동기 및 비동기 반복 경계를 제공해야 하며, 각 묶음의 상태·조회 제한·오프셋을 유지해야 한다.
- SRS-GET-021: 제품은 문서 본문을 호출자 제공 출력 대상으로 복사하는 동기 및 비동기 고수준 경로를 제공해야 한다. 제품이 연 본문 스트림은 정상 완료·읽기·쓰기 실패 및 취소 시 정리하고, 호출자 제공 출력 대상은 닫지 않아야 한다.
- SRS-GET-022: 본문 복사 결과는 복사한 문서 식별자와 바이트 수 및, 검증이 요청되거나 문서 정보에 존재하는 경우, SHA-256 확인 결과를 제공해야 한다. 크기 또는 체크섬 불일치는 `ConsistencyError`로 구분해야 한다.
- SRS-GET-023: 일반·관리 단건 문서 정보 조회와 본문·본문 스트림 조회는 개인 또는 그룹 문서 파티션을 필수로 받아야 한다. 제품은 처음부터 문서 파티션과 문서 식별자를 함께 조회 조건으로 사용해야 하며, 다른 파티션에만 존재하는 문서는 `DocumentNotFoundError`로 처리해야 한다.
- SRS-GET-024: 목록 커서는 파티션 종류와 식별값을 포함한 조회 조건에 결합해야 한다. 다른 종류 또는 다른 식별값의 파티션에서 커서를 재사용하면 `ValidationError`로 거부해야 한다.
- SRS-GET-025: 일반 문서 목록과 복구 대상 목록은 지정된 문서 파티션의 항목만 정렬과 페이지 제한 전에 선택해야 하며, 다른 파티션의 항목은 오류를 발생시키거나 존재 여부를 노출하지 않고 결과에서 제외해야 한다.

### 3.5 문서 삭제

- SRS-DEL-001: 제품은 논리 삭제와 완전 삭제를 지원해야 한다.
- SRS-DEL-002: 삭제는 본문 삭제와 문서 정보 상태 변경 또는 제거를 일관된 순서로 처리해야 한다.
- SRS-DEL-003: 삭제 중 본문 삭제에 실패하면 문서 정보에 실패 상태를 남겨 불완전한 상태를 식별할 수 있어야 한다.
- SRS-DEL-004: 본문 삭제 후 문서 정보 처리에 실패하면 삭제 진행 상태를 남겨 복구 대상임을 식별할 수 있어야 한다.
- SRS-DEL-005: 논리 삭제와 완전 삭제는 각각 명시적인 공개 작업으로 제공해야 하며, 하나의 삭제 작업에서 완전 삭제 여부를 선택하는 방식도 지원해야 한다.
- SRS-DEL-006: 논리 삭제와 완전 삭제의 공개 결과는 문서 식별자, 삭제 수행 여부, 완전 삭제 여부 및 최종 상태를 포함하는 공식 결과 모델로 반환해야 하며, 해당 모델은 명시적으로 정의된 직렬화 결과를 제공해야 한다.
- SRS-DEL-007: 논리 삭제와 완전 삭제는 지정된 문서 파티션의 문서에만 적용해야 한다. 다른 파티션에만 존재하는 문서의 삭제 시도는 어떤 데이터도 변경하지 않고 `DocumentNotFoundError`로 처리해야 한다.

### 3.6 전체 데이터 삭제 및 데이터 적재 초기화

- SRS-RESET-001: 제품은 DMS 관리 데이터의 문서 정보, `documents/` prefix 아래의 문서 본문 및 설정된 업로드 작업 기록을 개별 문서의 논리 삭제가 아닌 전체 범위 완전 삭제로 처리해야 한다.
- SRS-RESET-002: 전체 데이터 삭제는 문서 정보가 없는 orphan 본문도 정리해야 하며, DMS prefix 밖의 다른 bucket 데이터는 삭제하지 않아야 한다.
- SRS-RESET-003: 제품은 전체 데이터 삭제 결과로 문서 정보, 문서 본문 및 업로드 작업 기록의 저장소별 삭제 건수와 합계 건수를 제공해야 하며, 해당 결과는 JSON 호환 직렬화와 JSON Schema를 제공해야 한다.
- SRS-RESET-004: 제품은 기존 DMS 관리 데이터를 비우고 새로운 데이터 적재를 시작하는 데이터 적재 초기화 작업을 제공해야 한다. 초기화는 이미 빈 상태에서도 성공해야 하며, 완료 결과에 새 적재를 시작할 수 있는 상태를 표시해야 한다.
- SRS-RESET-005: 문서 정보 저장소, 본문 저장소 및 업로드 작업 저장소는 분산 트랜잭션으로 가장하지 않아야 한다. 한 저장소의 삭제가 실패해도 나머지 저장소 삭제를 시도하고, 부분 삭제 건수와 실패 저장소 목록을 포함한 구분 가능한 오류를 제공해야 한다. 부분 실패 결과는 새 데이터 적재 준비 완료로 표시해서는 안 된다.
- SRS-RESET-006: 전체 및 파티션별 데이터 삭제·데이터 적재 초기화는 작업 관찰자에 성공·실패 결과를 전달해야 한다. 접근 정책이 제공된 경우 제품은 네 관리 작업에 대한 정책 판정을 거쳐야 하며, 인증과 정책 규칙의 소유권은 호스트에 있어야 한다.
- SRS-RESET-007: 전체 데이터 삭제 및 데이터 적재 초기화는 동기 공개 경계와 동일한 결과·오류·부분 실패 의미를 갖는 비동기 공개 경계를 제공해야 한다.
- SRS-RESET-008: 제품은 특정 문서 파티션의 데이터 삭제·적재 초기화와 모든 문서 파티션의 데이터 삭제·적재 초기화를 서로 다른 명시적 관리 작업으로 제공해야 한다. 파티션별 작업은 해당 파티션의 문서 정보, 문서 본문 및 멱등성 작업 기록만 삭제하고 다른 파티션의 데이터를 변경하지 않아야 하며, 일반 문서 작업에서 파티션 생략을 전체 범위 의미로 해석해서는 안 된다.

### 3.7 상태 점검 및 복구

- SRS-REC-001: 제품은 문서 정보의 존재 여부, 문서 본문의 존재 여부, 문서 상태 및 일관성 판단 결과를 제공해야 한다.
- SRS-REC-002: 문서 정보가 없는 점검 요청은 문서 없음 오류가 아닌 점검 결과로 제공해야 한다.
- SRS-REC-003: 삭제 진행 상태에서 본문이 이미 제거된 문서의 삭제 완료 처리를 지원해야 하며, 논리 완료와 완전 완료를 구분해야 한다.
- SRS-REC-004: 문서 정보는 존재하지만 본문이 없는 문서를 실패 상태로 표시하는 복구를 지원해야 한다.
- SRS-REC-005: 문서 정보 없이 남은 본문을 호출자가 명시적으로 제공한 저장 위치를 기준으로 제거하는 복구를 지원해야 한다.
- SRS-REC-006: 복구는 실제 변경 없이 결과를 미리 확인하는 실행 방식을 지원해야 하며, 미리보기 결과에서 내보낸 계획은 실행 전에 다시 검증해야 한다.
- SRS-REC-007: 제품은 실패 또는 삭제 진행 상태의 문서를 제한된 범위로 조회하고, 각 복구 항목의 성공 또는 실패 결과를 개별적으로 제공해야 한다.
- SRS-REC-008: 일괄 복구 결과는 조회·적격·적용·건너뜀·실패 수를 안정적으로 제공하고, 오류 처리 중 재점검까지 실패해도 나머지 항목 처리를 중단하지 않아야 한다. 복구 감사 callback의 실패는 복구 결과를 가리지 않아야 한다.
- SRS-REC-009: 문서 점검, 복구 대상 조회, 단건·일괄 복구 및 고아 본문 정리는 문서 파티션을 필수로 받고 해당 파티션의 문서 정보와 본문만 조회·변경해야 한다. 문서 정보가 필요한 단건 복구에서 다른 파티션에만 문서가 존재하면 `DocumentNotFoundError`를 제공해야 하며, 점검은 실제 부재와 다른 파티션을 구분하지 않고 문서 정보 없음 결과를 제공해야 한다.
- SRS-REC-010: 미리보기에서 생성한 복구 계획은 생성 당시의 문서 파티션에 결합되어야 하며, 다른 종류 또는 식별값의 파티션에서 실행하려는 요청은 변경 전에 `ValidationError`로 거부해야 한다.
- SRS-REC-011: 문서 정보가 없는 본문을 정리하는 복구는 제공된 저장 위치가 지정된 문서 파티션의 namespace에 속하는지 검증하고, 다른 파티션 또는 전체 DMS 범위의 본문을 삭제할 수 있는 위치는 거부해야 한다.

### 3.8 관찰 및 스트림 정리

- SRS-OPS-001: 제품은 등록, 공개·관리 조회, 커서 목록 조회, 본문 조회, 삭제, 전체 데이터 삭제·적재 초기화 및 상태 점검·복구의 완료와 실패 결과를 하나의 공통 작업 관찰자 계약으로 전달할 수 있어야 한다.
- SRS-OPS-002: 작업 관찰자 이벤트는 작업 종류, 성공 여부, 관련 문서 식별자 또는 목록 조건, 오류 코드, 시작·완료 시각을 포함해야 하며 문서 본문, 자격 증명, 내부 저장 위치 및 비밀 설정값을 포함하지 않아야 한다. 문서 파티션 식별값은 호스트의 공개 정책에 따라 필요한 경우에만 안전한 조건 정보로 전달해야 한다.
- SRS-OPS-003: 작업 관찰자의 실패는 원래 문서 작업의 성공 결과나 최초 실패를 변경하지 않아야 하며, 관찰 실패 자체는 구조화된 운영 로그에서 확인할 수 있어야 한다.
- SRS-OPS-004: 제품이 직접 연 파일과 문서 본문 스트림은 정상 소진, 예외, 취소 및 조기 종료에서 안전하게 정리해야 하며, 반복 종료 호출에 안전해야 한다.
- SRS-OPS-005: 호출자가 제공한 입력 스트림과 출력 대상은 제품이 닫지 않아야 하며, SDK가 직접 연 스트림과 소유권 경계를 구분해야 한다.

### 3.9 비동기 실행

- SRS-ASY-001: 제품은 문서 등록, 등록 작업 상태 조회, 공개·관리 문서 정보 조회, 문서 본문 조회, 커서 목록 조회, 논리·완전 삭제, 전체 데이터 삭제 및 데이터 적재 초기화, 상태 점검·복구를 포함한 모든 공개 SDK 작업에 대응하는 비동기 호출 경계를 제공해야 한다.
- SRS-ASY-002: 비동기 호출은 대응하는 동기 호출과 동일한 공식 공개 결과 모델, 입력 검증, 오류 코드, 상태 전이, 멱등성 및 부분 실패 정합성 계약을 적용해야 한다.
- SRS-ASY-003: 비동기 호출은 저장소 접근이나 동기 정리 작업으로 호스트의 이벤트 루프를 직접 차단하지 않아야 한다.
- SRS-ASY-004: 비동기 호출은 취소가 하위 동기 작업을 실제로 중단하는지 여부를 명확히 구분해야 한다. 이미 시작한 변경 작업을 안전하게 중단할 수 없으면 정합성 경계까지 완료한 뒤 취소를 전달하고, 호출자가 최종 작업 상태를 조회할 수 있어야 하며 취소를 원상 복구 완료로 표현하지 않아야 한다.
- SRS-ASY-005: 비동기 공개 경계는 문서 등록·파일 등록·스트림 등록, 공개·관리 조회, 목록·전체 순회, 본문 스트리밍·복사, 삭제, 전체 데이터 삭제·적재 초기화 및 상태 점검·복구를 awaitable 또는 비동기 반복 방식으로 제공해야 한다.
- SRS-ASY-006: 비동기 공개 경계는 동기 공개 경계와 동일한 문서 업무 로직, 상태 전이, 결과·오류·멱등성·복구 의미를 유지하고, SQLAlchemy 세션과 본문 저장소 처리는 비동기 adapter 경계로 분리해야 한다.
- SRS-ASY-007: 비동기 공개 경계는 개인·그룹 문서 파티션 격리, 파티션이 결합된 커서 검증, 파티션별 멱등성, 복구 및 파티션별 데이터 삭제를 동기 공개 경계와 동일하게 적용해야 한다.


### 3.10 호스트 통합 경계

- SRS-INT-001: 제품은 등록, 조회, 목록, 삭제, 전체 데이터 삭제·적재 초기화 및 복구 기능을 각각 표현하는 기능별 공개 계약과 이들을 결합한 전체 문서 관리 계약을 제공해야 한다.
- SRS-INT-002: 기능별 공개 계약은 공식 요청·결과·오류 모델만 사용해야 하며, 호스트의 테스트 대역이 구체 SDK 구현이나 내부 모듈을 상속·가져오기하지 않고 계약을 충족할 수 있어야 한다.
- SRS-INT-003: 등록, 일반·관리 조회, 목록, 본문·스트림·복사, 논리·완전 삭제, 점검 및 복구를 포함한 일반 문서 작업은 호출마다 하나의 문서 파티션을 필수로 받아야 하며, 접근 제어를 사용하는 호출은 호출별 접근 맥락을 선택적으로 받아야 한다. 제품은 공유 SDK 객체에 변경 가능한 현재 파티션이나 접근 맥락을 저장하지 않아야 한다.
- SRS-INT-004: 제품은 문서 파티션을 데이터 라우팅과 격리 목적으로 사용해야 하며, 인증, 사용자·그룹 조회 또는 그룹 소속 확인은 수행하지 않아야 한다. 접근 정책이 제공된 경우 제품은 해당 정책으로 문서 작업의 허용 여부를 판단해야 하며, 호스트는 호출자가 지정된 파티션을 사용할 수 있는지 확인한 뒤 신뢰 파티션과 접근 맥락을 전달해야 한다.
- SRS-INT-005: 문서 목록과 복구 대상 목록은 문서 파티션 조건을 정렬과 페이지 제한보다 먼저 적용해야 하며, 파티션 안에서 커서 순서, 페이지 크기, 다음 커서 및 추가 결과 여부의 의미를 유지해야 한다.
- SRS-INT-006: 문서 파티션 식별값은 호스트가 해석하는 비어 있지 않은 불투명 문자열이어야 하며, 제품은 개인과 그룹 이외의 파티션 종류를 허용하거나 특정 식별값 형식을 가정하지 않아야 한다.
- SRS-INT-009: 특정 웹 프레임워크용 응답, 예외 처리기, 업로드 어댑터 및 애플리케이션 생명주기 연결은 핵심 제품과 분리해야 한다. 해당 연계 계층은 기능별 공개 계약, 종료 보장 스트림 및 공개 데이터 전송 모델만으로 구현할 수 있어야 한다.

## 4. 데이터 및 상태 요구사항

- SRS-DAT-001: 문서 정보는 문서 식별자, 문서 파티션, 원본 파일명, 콘텐츠 유형, 파일 크기, 저장 위치, 상태, 생성·수정 시각을 보존해야 한다.
- SRS-DAT-002: 문서 정보는 선택적 체크섬, 삭제 시각, 작성자 및 호출자 부가 정보를 보존할 수 있어야 한다. 호출자 부가 정보는 JSON 객체로 저장하며, DMS는 키·값의 업무적 의미와 특정 업무 스키마를 해석하지 않아야 한다.
- SRS-DAT-003: 문서 상태는 사용 가능, 삭제 진행, 삭제 완료 및 실패 상태를 구분해야 한다.
- SRS-DAT-004: 정상 등록이 완료된 문서는 사용 가능 상태여야 한다.
- SRS-DAT-005: `UPLOADED` 상태는 과거 데이터 호환을 위한 값이며 정상 등록 흐름에서 새로 생성하지 않아야 한다. 새 문서에는 `AVAILABLE` 상태를 사용해야 한다.
- SRS-DAT-006: 공개 문서 정보는 내부 저장 위치를 제외한 문서 식별자, 문서 파티션, 원본 파일명, 콘텐츠 유형, 파일 크기, 상태, 생성·수정 시각, 선택적 체크섬·삭제 시각·작성자 및 호출자 부가 정보를 포함하는 공식 모델이어야 한다.
- SRS-DAT-007: 공개 문서 정보, 문서 페이지, 등록 결과, 삭제 결과 및 전체 데이터 삭제 결과의 시스템 관리 필드는 열거 상태를 문자열 값으로, 날짜·시각을 시간대가 포함된 표준 문자열로 변환해야 하며 공개 문서 정보와 그 중첩 모델에 내부 저장 위치를 포함하지 않아야 한다. 호출자 부가 정보는 JSON 객체로 포함하며 DMS가 업무 스키마에 따라 정규화하지 않아야 한다.
- SRS-DAT-008: 공개 문서 정보, 문서 페이지, 등록 결과, 삭제 결과 및 전체 데이터 삭제 결과는 각각 기준 공개 데이터 전송 모델과 호환 dump를 제공해야 한다. 호출자 부가 정보는 JSON 객체로 저장·반환해야 한다.
- SRS-DAT-009: JSON Schema를 제공하는 공식 공개 데이터 전송 모델은 시스템 관리 필드의 필드명, 필수 여부, 자료형 및 중첩 구조를 설명해야 하며, 호출자 부가 정보는 JSON 객체임을 설명하되 내부 업무 구조나 키의 의미를 제한하지 않아야 한다.
- SRS-DAT-010: 내부 저장 위치는 공개 문서 정보 모델의 정의에 구조적으로 존재하지 않아야 하며, 문서 페이지나 등록 결과에 중첩된 공개 문서 정보에도 같은 규칙을 적용해야 한다. 관리·복구 전용 점검 결과는 필요한 경우 저장 위치를 포함할 수 있다.
- SRS-DAT-011: SDK 속성명과 외부 직렬화 필드명이 다르면 하나의 명시적인 serialization alias 또는 공용 dump 규칙을 제공해야 한다. 부가 정보의 SDK 속성명 `extra_metadata`는 canonical 외부 필드명 `metadata`로 직렬화하고, 기존 호환 형식은 별도로 식별해야 한다.
- SRS-DAT-012: 상태 확인, 문서 점검, 복구 계획·실행, 작업 관찰 및 업로드 작업 상태를 포함한 나머지 공식 공개 결과 모델도 시스템 관리 필드의 일관된 직렬화 규칙을 제공해야 하며, 관리·복구 결과에 포함된 내부 저장 위치는 일반 공개 결과와 혼합하지 않아야 한다. 호출자 부가 정보는 변환 대상에서 제외한다.
- SRS-DAT-013: 모든 공식 공개 결과 모델의 시스템 관리 필드에 대한 직렬화 작업명과 날짜·시각, 열거값 및 선택적 값 변환 규칙은 일관되어야 하며, 호출자 부가 정보에는 DMS가 별도의 표현 규칙을 적용하지 않아야 한다.
- SRS-DAT-014: 모든 문서 정보는 null이 아닌 하나의 문서 파티션을 보존해야 하며, 공개 문서 정보·등록 결과·목록 결과 및 JSON Schema에서 파티션 종류와 식별값을 확인할 수 있어야 한다. 파티션이 없거나 개인과 그룹이 동시에 지정된 문서 상태를 허용하지 않아야 한다.
- SRS-DAT-015: 문서 식별자는 모든 파티션에서 전역으로 유일해야 하며, 이미 다른 파티션에 존재하는 식별자를 새 문서에 재사용하려는 등록은 중복으로 처리해야 한다.
- SRS-DAT-016: 문서 본문 저장 namespace는 파티션 종류와 식별값을 모두 구분해야 한다. 같은 식별값을 가진 개인 파티션과 그룹 파티션 또는 서로 다른 파티션의 본문 경로가 충돌하지 않아야 한다.
- SRS-DAT-017: 문서 정보 저장소의 단건 조회·상태 변경·삭제 조건은 문서 파티션 종류, 파티션 식별값 및 문서 식별자를 함께 사용해야 하며, 파티션별 목록 조회에 안정적인 복합 정렬과 인덱스를 제공해야 한다.
- SRS-DAT-018: 새 파티션 계약은 파티션이 없는 과거 문서 정보, 과거 사용자 범위 저장 경로, 과거 커서 및 과거 멱등성 기록을 읽거나 변환하는 호환·자동 이전 동작을 제공하지 않아야 한다.

## 5. 비기능 요구사항

- SRS-NFR-001: 공개 API는 호출자가 입력 유효성, 접근 거부, 중복, 문서 없음, 삭제 상태, 객체 저장소 오류, 문서 정보 저장소 오류, 설정 오류, 멱등성 충돌·진행 상태 및 불일치를 구분할 수 있는 오류 유형을 제공해야 한다. 접근 거부는 `AccessDeniedError`와 안정된 오류 코드로 반환해야 한다.
- SRS-NFR-002: 문서 처리와 복구는 부분 실패가 발생해도 원인과 후속 조치 판단에 필요한 상태를 보존해야 한다.
- SRS-NFR-003: 자동화된 검증은 등록, 조회, 삭제, 전체 데이터 삭제, 상태 점검, 복구 및 component 조립의 핵심 흐름을 포함해야 한다.
- SRS-NFR-004: 실제 저장소 연동 검증은 준비된 외부 서비스를 재사용해야 하며, 외부 서비스가 준비되지 않은 환경에서는 해당 검증을 명확히 구분해야 한다. 검증을 위해 제품이 Docker Compose 또는 별도 인프라를 생성하지 않아야 한다.
- SRS-NFR-005: 사용자 안내 문서, 제품 요구사항 및 본 문서는 제품의 실제 제공 범위와 일치해야 한다.
- SRS-NFR-006: 기본 공개 등록 및 조회 결과의 문서 정보는 내부 저장 위치를 포함하지 않아야 한다.
- SRS-NFR-008: 내보낸 복구 계획 실행은 각 작업 직전에 현재 상태를 재점검해야 하며, 복구 감사 callback 실패는 복구 결과를 가리지 않아야 한다.
- SRS-NFR-009: 모든 공개 SDK 오류는 예외 유형과 별개로 안정된 기계 판독용 오류 코드, 상위 오류 분류 및 재시도 가능 여부를 제공해야 한다. 동일한 실패 의미는 진입점이나 하위 저장소 구현과 관계없이 같은 코드와 분류를 사용해야 하며, 새 오류 코드 추가는 기존 코드의 의미를 변경하지 않아야 한다.
- SRS-NFR-010: 자동화된 공개 계약 검증은 패키지 최상위 공개 경계에서 기능별 계약, component 조립 정책, 호스트 제공 접근 정책, 파일·일반 입력 등록, 전체 목록 순회, 본문 복사, 필수 문서 파티션, 동기·비동기 공개 경계, 스트림 정리 및 작업 관찰자 동작을 확인해야 한다.
- SRS-NFR-011: 자동화된 공개 계약 검증은 개인·그룹 문서·본문·멱등성 작업 격리, 같은 식별값의 종류 구분, 다른 파티션의 커서 거부와 문서 없음 처리, 복구 계획 결합 및 파티션별 데이터 삭제를 동기·비동기 경계에서 확인해야 한다.

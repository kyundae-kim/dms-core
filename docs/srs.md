# 소프트웨어 요구사항 정의서

## 1. 목적 및 적용 범위

본 문서는 문서 관리 공통 구성요소가 충족해야 하는 소프트웨어 요구사항을 정의한다. 본 제품은 다른 업무 시스템에 통합되어 사용하는 Python SDK이며 독립 실행형 API 서버가 아니다.

제품은 호출자가 이미 생성한 저장소 연결 또는 문서 정보 저장소·문서 본문 저장소의 공개 구성요소를 주입받아 문서 작업을 수행해야 한다. 제품은 환경변수에서 인프라 연결을 읽거나 저장소 client를 생성하는 구성 경계를 제공하지 않아야 한다.

## 2. 용어

- 문서 본문: 파일의 실제 바이트 데이터와 관련 속성이다.
- 문서 정보: 문서 식별자, 원본 파일명, 콘텐츠 유형, 크기, 저장 위치, 상태, 생성·수정 시각 및 부가 정보이다.
- 논리 삭제: 문서 정보를 보존한 채 문서를 삭제된 상태로 표시하는 처리이다.
- 완전 삭제: 문서 본문과 문서 정보를 모두 제거하는 처리이다.
- DMS 관리 데이터: DMS가 관리하는 문서 정보, `documents/` prefix 아래의 문서 본문 및 설정된 업로드 작업 기록이다.
- 데이터 적재 초기화: 기존 DMS 관리 데이터를 비우고 새로운 데이터 묶음을 적재할 수 있는 빈 상태를 만드는 관리 작업이다.
- 불일치 상태: 문서 본문과 문서 정보의 존재 여부 또는 문서 상태가 서로 맞지 않는 상태이다.
- 커서 페이지네이션: 정렬 기준상의 마지막 위치를 불투명한 값으로 전달하여 다음 결과 묶음을 조회하는 방식이다.
- 종료 보장 반복자: 전체 소비와 읽기 실패 때 자동으로 자원을 정리하고, 일부 소비 후에는 명시적인 종료를 통해 즉시 정리할 수 있는 반복자이다.
- 비동기 공개 경계: 동기 공개 작업과 동일한 결과·오류·정합성 계약을 비동기 호출 방식으로 제공하는 경계이다.
- 공개 데이터 전송 모델: 호스트 시스템이 내부 저장소 모델을 다시 선언하지 않고 직렬화와 스키마 생성에 사용할 수 있는 공식 공개 결과 형식이다.
- 호출자 소유 자원: 호출자가 생성·관리하며 SDK가 종료하지 않는 저장소 연결 또는 관련 자원이다.
- SDK 소유 자원: 호출자가 SDK에 종료 책임을 명시적으로 위임하여 SDK가 조립 실패와 종료 시 정리하는 자원이다.
- 접근 맥락: 호스트가 호출 단위로 제공하는 불투명한 주체, 조직 및 역할 정보이다.
- 접근 정책: 접근 맥락과 작업 종류를 바탕으로 허용, 거부 또는 목록 범위 제한을 결정하는 호스트 제공 규칙이다.
- 호출 범위 작업 맥락: 작성자, 멱등성 범위, 감사 행위자 및 기본 부가 정보처럼 한 작업 범위에 적용되는 변경 불가능한 값의 묶음이다.
- 작업 관찰자: 문서 작업의 완료 또는 실패 정보를 로깅·감사·측정 체계로 전달하는 선택적 호스트 제공 경계이다.
- 전송 방식 중립 오류 설명자: SDK 오류의 코드, 분류, 재시도 가능 여부 및 외부 메시지를 통신 프로토콜과 분리하여 표현하는 공개 형식이다.

## 3. 기능 요구사항

### 3.1 조립 및 자원 생명주기

- SRS-CFG-001: 제품은 호출자가 이미 생성한 관계형 저장소 연결과 객체 저장소 client를 이용하는 client 기반 조립과, 완성된 문서 정보 저장소·문서 본문 저장소 구성요소를 주입하는 component 기반 조립을 제공해야 한다. 두 경로 모두 환경변수에서 client를 생성하거나 읽지 않아야 한다.
- SRS-CFG-002: client 기반 조립은 PostgreSQL 또는 SQLite dialect를 사용하는 저장소 연결과 비어 있지 않은 버킷 이름을 받아야 하며, 지원하지 않는 dialect 또는 빈 버킷 이름은 조립 전에 `ConfigurationError`로 거부해야 한다.
- SRS-CFG-003: component 기반 조립은 문서 정보 저장소와 문서 본문 저장소를 필수로 받고, 업로드 작업 저장소는 선택적으로 받을 수 있어야 한다. 업로드 작업 저장소가 없으면 영속 멱등성 작업을 요구하는 기능은 구분 가능한 유효성 오류를 제공해야 한다.
- SRS-CFG-004: 제품은 모든 조립 경로에 최대 파일 크기, 부가 정보 검증기와 검증 한도, 로거, 시작 상태 확인과 제한 시간, 복구 감사 경계, 작업 관찰자 및 접근 정책을 포함하는 공통 조립 정책을 적용할 수 있어야 한다. 양수여야 하는 정책 값은 조립 전에 검증해야 한다.
- SRS-CFG-005: 시작 상태 확인은 기본적으로 비활성화할 수 있어야 하며, 활성화된 경우 구성된 각 의존 요소의 확인 실패와 제한 시간 초과를 실패한 대상·원인·재시도 가능 여부를 확인할 수 있는 `HealthCheckFailedError`로 제공해야 한다.
- SRS-CFG-006: 호출자가 제공한 연결·구성요소는 기본적으로 호출자 소유여야 하며, SDK는 명시적으로 등록된 종료 callback 또는 SDK 소유로 지정된 `ManagedResource`만 종료해야 한다.
- SRS-CFG-007: SDK 소유 자원은 등록 순서의 역순으로 정상 종료와 조립 실패 시 정확히 한 번 정리해야 한다. 한 자원의 종료가 실패해도 나머지 자원의 정리를 계속 시도하고, 여러 실패를 개별 확인할 수 있는 `ResourceCleanupError`를 제공해야 한다.
- SRS-CFG-008: 조립 또는 시작 상태 확인이 실패하면 이미 SDK 소유로 등록된 자원을 정리하고 최초 조립 실패를 보존해야 하며, 호출자가 제공한 저장소 연결은 명시적으로 SDK 소유로 위임되지 않은 한 종료하지 않아야 한다.

### 3.2 문서 등록

- SRS-UPL-001: 제품은 문서 본문, 파일명, 콘텐츠 유형, 선택적 문서 식별자, 부가 정보 및 작성자 정보를 받아 문서를 등록해야 한다.
- SRS-UPL-002: 제품은 메모리의 바이트 데이터와 정확한 양수 크기가 선언된 동기 바이너리 스트림을 통한 등록을 지원해야 한다.
- SRS-UPL-003: 스트림 등록 시 실제 읽은 크기가 선언된 크기와 일치하는지 검증해야 한다.
- SRS-UPL-004: 제품은 업로드 과정에서 등록 본문의 SHA-256을 계산해야 하며, 파일 및 스트림 등록의 문서 정보에 계산된 체크섬을 보존해야 한다. 바이트 등록은 요청에 제공된 선택적 체크섬을 등록 결과에 반영할 수 있어야 한다.
- SRS-UPL-005: 제품은 빈 본문, 유효하지 않은 파일명·콘텐츠 유형·문서 식별자·작성자·크기·스트림 또는 부가 정보를 저장 전에 거부해야 한다.
- SRS-UPL-006: 최대 파일 크기 제한이 설정된 경우 바이트, 파일 및 스트림 등록에 동일하게 적용하고, 제한 초과는 `PayloadTooLargeError`로 구분해야 한다.
- SRS-UPL-007: 제품은 중복 문서 식별자로 등록하려는 요청을 구분 가능한 `DuplicateDocumentError`로 처리해야 한다.
- SRS-UPL-008: 본문 저장 후 문서 정보 저장에 실패하면 저장된 본문을 정리해야 한다. 본문 정리에도 실패하면 불일치 상태를 나타내는 `ConsistencyError`를 제공해야 한다.
- SRS-UPL-009: 바이트 등록에 멱등성 키가 제공되면 동일한 범위와 동일한 요청에 대한 완료 결과를 재사용하고, 진행 중인 요청은 재시도 가능한 상태로 구분해야 한다.
- SRS-UPL-010: 바이트 등록 요청에서 멱등성 키를 사용하려면 비어 있지 않은 멱등성 범위와 영속적인 업로드 작업 저장소를 함께 제공해야 하며, 조건을 충족하지 못한 요청은 저장 작업 전에 유효성 오류로 거부해야 한다.
- SRS-UPL-011: 제품은 바이트 데이터, 파일 경로 및 정확한 양수 크기가 선언된 동기 바이너리 스트림의 세 입력 범주를 지원해야 한다.
- SRS-UPL-012: 스트림 등록은 실제 읽은 크기가 선언 크기와 다르면 문서 정보를 저장하지 않고 업로드된 본문을 정리해야 하며, 호출자가 제공한 스트림을 닫지 않아야 한다.
- SRS-UPL-013: 세 등록 범주는 파일명, 콘텐츠 유형, 문서 식별자, 작성자 및 부가 정보처럼 공통으로 받는 입력에 동일한 정규화와 검증 규칙을 적용하고 저장 작업 전에 동일한 유효성 오류로 거부해야 한다.
- SRS-UPL-014: 크기를 알 수 없는 입력 스트림과 비동기 입력 스트림은 등록 입력으로 지원하지 않아야 한다.
- SRS-UPL-015: 스트림 등록 요청은 요청별 최대 크기, 읽기 단위 조절, 호출자 제공 체크섬 또는 멱등성 값을 받지 않아야 하며, 제품 최대 파일 크기는 모든 등록 범주에 공통으로 적용해야 한다.
- SRS-UPL-016: 제품은 파일 경로를 받아 문서를 등록하는 고수준 경로를 제공해야 하며 파일 열기와 닫기, 실제 크기 확인, SHA-256 계산 및 콘텐츠 유형 추론을 소유해야 한다.
- SRS-UPL-017: 파일 경로 등록은 파일명, 콘텐츠 유형, 문서 식별자, 작성자 및 부가 정보에 기존 등록 경로와 동일한 정규화, 검증, 중복 및 부분 실패 계약을 적용해야 한다.
- SRS-UPL-018: 파일 경로 등록에서 자동으로 결정한 파일명, 크기, 체크섬 및 콘텐츠 유형은 등록 결과를 통해 호출자가 확인할 수 있어야 하며, 공개 결과에는 내부 저장 위치가 포함되지 않아야 한다.

### 3.3 문서 조회 및 본문 전달

- SRS-GET-001: 제품은 문서 식별자로 삭제되지 않은 문서 정보를 조회해야 하며, 논리 삭제 또는 삭제 진행 상태인 문서는 일반 공개 조회에서 문서 없음으로 처리해야 한다.
- SRS-GET-002: 제품은 문서 식별자로 문서 본문을 조회해야 하며, 메모리 반환과 스트림 반환을 지원해야 한다.
- SRS-GET-003: 동기 문서 본문 스트림은 반복 단위로 읽을 수 있고, 사용 종료 시 관련 자원을 해제할 수 있어야 한다.
- SRS-GET-004: 제품은 문서 상태를 기준으로 문서 정보를 목록 조회할 수 있어야 하며, 일반 공개 목록은 삭제 완료 및 삭제 진행 상태의 문서를 제외해야 한다. 일반 공개 목록은 커서 방식만 허용하고 오프셋 입력을 허용하지 않아야 한다.
- SRS-GET-005: 존재하지 않는 문서 정보 조회는 `DocumentNotFoundError`로 처리해야 한다.
- SRS-GET-006: 문서 정보는 존재하나 본문을 읽을 수 없으면 `ConsistencyError`로 처리해야 한다.
- SRS-GET-007: 기본 공개 목록은 생성 시각과 문서 식별자의 내림차순 복합 순서를 사용해야 한다. 불투명 커서는 상태 필터와 페이지 크기에 결합되어야 하며 결과는 항목, 다음 커서 및 추가 결과 여부를 포함해야 한다. 첫 조회는 커서 없이 시작하고 마지막 페이지의 다음 커서는 없어야 한다.
- SRS-GET-008: 제품은 정확한 멱등성 범위와 키로 업로드 작업의 구조화된 상태를 조회해야 하며, 작업이 없으면 `UploadOperationNotFoundError`를 제공해야 한다.
- SRS-GET-009: 일반 등록 결과, 문서 정보 조회 및 목록 결과는 내부 저장 위치를 포함하지 않는 공개용 문서 정보를 기본으로 반환해야 한다.
- SRS-GET-010: 내부 저장 위치를 포함하는 문서 정보 접근은 복구·관리 용도의 명시적 접근 경로로 분리해야 한다.
- SRS-GET-011: 논리 삭제 또는 삭제 진행 상태인 문서의 본문 및 본문 스트림 조회는 저장소 불일치가 아닌 `DocumentDeletedError`로 거부해야 하며, 삭제 상태 확인은 명시적 관리·복구 조회에서만 허용해야 한다.
- SRS-GET-012: 일반 공개 단건 조회와 커서 목록 조회는 삭제 문서 은닉 정책을 일관되게 적용해야 하며, 호출자가 일반 조회의 상태 조건으로 삭제 완료·삭제 진행 문서를 노출하거나 오프셋 경로를 사용하여 정책을 우회할 수 없어야 한다.
- SRS-GET-013: 제품은 문서 본문을 비동기 반복 가능한 스트림으로 조회하는 인터페이스를 제공해야 하며, 전체 본문을 메모리에 적재하도록 강제하지 않아야 한다.
- SRS-GET-014: 비동기 문서 본문 스트림은 비동기 컨텍스트 관리와 명시적 비동기 종료를 지원하고, 정상 종료·예외·취소·일부 읽기 후 종료에서 관련 자원을 해제해야 한다.
- SRS-GET-015: 커서 페이지 크기는 1 이상 1000 이하로 제한해야 하며, 변조되었거나 현재 조회 조건과 일치하지 않는 커서는 구분 가능한 유효성 오류로 거부해야 한다.
- SRS-GET-016: 동기 문서 본문 스트림은 전체 소비 완료와 읽기 오류에서 소유 자원을 자동으로 정리하는 종료 보장 반복 경로를 제공해야 한다. 일부 소비 후 조기 종료를 위해 반복 호출에 안전한 명시적 종료를 지원하고, 정리 실패가 최초 읽기 오류를 가리지 않아야 한다.
- SRS-GET-017: 비동기 문서 본문 스트림은 전체 소비 완료, 읽기 오류 및 소비 작업 취소에서 소유 자원을 비동기적으로 정리하는 종료 보장 반복 경로를 제공해야 한다. 일부 소비 후 조기 종료를 위해 반복 호출에 안전한 명시적 비동기 종료를 지원해야 한다.
- SRS-GET-018: 종료 보장 반복 경로는 호스트 프레임워크가 문서 본문 스트림 객체의 컨텍스트 관리자에 직접 진입하지 않고 반환된 반복자만 소비하는 경우에도 적용할 수 있어야 한다. 전송 계층의 조기 중단은 반복자의 명시적 종료를 통해 즉시 정리할 수 있어야 한다.
- SRS-GET-019: 제품은 호출자가 커서를 직접 관리하지 않고 문서 전체를 순회하는 동기 및 비동기 반복 경계를 제공해야 하며, 최초 페이지의 상태 필터와 페이지 크기를 모든 후속 페이지에 유지해야 한다.
- SRS-GET-020: 제품은 호출자가 커서를 직접 관리하지 않고 복구 대상을 제한된 묶음으로 순회하는 동기 및 비동기 반복 경계를 제공해야 하며, 각 묶음의 상태·조회 제한·오프셋을 유지해야 한다.
- SRS-GET-021: 제품은 문서 본문을 호출자 제공 출력 대상으로 복사하는 동기 및 비동기 고수준 경로를 제공해야 한다. 제품이 연 본문 스트림은 정상 완료·읽기·쓰기 실패 및 취소 시 정리하고, 호출자 제공 출력 대상은 닫지 않아야 한다.
- SRS-GET-022: 본문 복사 결과는 복사한 문서 식별자와 바이트 수 및, 검증이 요청되거나 문서 정보에 존재하는 경우, SHA-256 확인 결과를 제공해야 한다. 크기 또는 체크섬 불일치는 `ConsistencyError`로 구분해야 한다.

### 3.4 문서 삭제

- SRS-DEL-001: 제품은 논리 삭제와 완전 삭제를 지원해야 한다.
- SRS-DEL-002: 삭제는 본문 삭제와 문서 정보 상태 변경 또는 제거를 일관된 순서로 처리해야 한다.
- SRS-DEL-003: 삭제 중 본문 삭제에 실패하면 문서 정보에 실패 상태를 남겨 불완전한 상태를 식별할 수 있어야 한다.
- SRS-DEL-004: 본문 삭제 후 문서 정보 처리에 실패하면 삭제 진행 상태를 남겨 복구 대상임을 식별할 수 있어야 한다.
- SRS-DEL-005: 논리 삭제와 완전 삭제는 각각 명시적인 공개 작업으로 제공해야 하며, 하나의 삭제 작업에서 완전 삭제 여부를 선택하는 방식도 지원해야 한다.
- SRS-DEL-006: 논리 삭제와 완전 삭제의 공개 결과는 문서 식별자, 삭제 수행 여부, 완전 삭제 여부 및 최종 상태를 포함하는 공식 결과 모델로 반환해야 하며, 해당 모델은 명시적으로 정의된 직렬화 결과를 제공해야 한다.

### 3.5 전체 데이터 삭제 및 데이터 적재 초기화

- SRS-RESET-001: 제품은 DMS 관리 데이터의 문서 정보, `documents/` prefix 아래의 문서 본문 및 설정된 업로드 작업 기록을 개별 문서의 논리 삭제가 아닌 전체 범위 완전 삭제로 처리해야 한다.
- SRS-RESET-002: 전체 데이터 삭제는 문서 정보가 없는 orphan 본문도 정리해야 하며, DMS prefix 밖의 다른 bucket 데이터는 삭제하지 않아야 한다.
- SRS-RESET-003: 제품은 전체 데이터 삭제 결과로 문서 정보, 문서 본문 및 업로드 작업 기록의 저장소별 삭제 건수와 합계 건수를 제공해야 하며, 해당 결과는 JSON 호환 직렬화와 JSON Schema를 제공해야 한다.
- SRS-RESET-004: 제품은 기존 DMS 관리 데이터를 비우고 새로운 데이터 적재를 시작하는 데이터 적재 초기화 작업을 제공해야 한다. 초기화는 이미 빈 상태에서도 성공해야 하며, 완료 결과에 새 적재를 시작할 수 있는 상태를 표시해야 한다.
- SRS-RESET-005: 문서 정보 저장소, 본문 저장소 및 업로드 작업 저장소는 분산 트랜잭션으로 가장하지 않아야 한다. 한 저장소의 삭제가 실패해도 나머지 저장소 삭제를 시도하고, 부분 삭제 건수와 실패 저장소 목록을 포함한 구분 가능한 오류를 제공해야 한다. 부분 실패 결과는 새 데이터 적재 준비 완료로 표시해서는 안 된다.
- SRS-RESET-006: 전체 데이터 삭제 및 데이터 적재 초기화는 호스트 접근 정책이 제공된 경우 관리 작업별 권한 판단을 거쳐야 하며, 작업 관찰자에 성공·실패 결과를 전달해야 한다.
- SRS-RESET-007: 전체 데이터 삭제 및 데이터 적재 초기화는 동기 공개 경계와 동일한 결과·오류·부분 실패 의미를 갖는 비동기 공개 경계를 제공해야 한다.

### 3.6 상태 점검 및 복구

- SRS-REC-001: 제품은 문서 정보의 존재 여부, 문서 본문의 존재 여부, 문서 상태 및 일관성 판단 결과를 제공해야 한다.
- SRS-REC-002: 문서 정보가 없는 점검 요청은 문서 없음 오류가 아닌 점검 결과로 제공해야 한다.
- SRS-REC-003: 삭제 진행 상태에서 본문이 이미 제거된 문서의 삭제 완료 처리를 지원해야 하며, 논리 완료와 완전 완료를 구분해야 한다.
- SRS-REC-004: 문서 정보는 존재하지만 본문이 없는 문서를 실패 상태로 표시하는 복구를 지원해야 한다.
- SRS-REC-005: 문서 정보 없이 남은 본문을 호출자가 명시적으로 제공한 저장 위치를 기준으로 제거하는 복구를 지원해야 한다.
- SRS-REC-006: 복구는 실제 변경 없이 결과를 미리 확인하는 실행 방식을 지원해야 하며, 미리보기 결과에서 내보낸 계획은 실행 전에 다시 검증해야 한다.
- SRS-REC-007: 제품은 실패 또는 삭제 진행 상태의 문서를 제한된 범위로 조회하고, 각 복구 항목의 성공 또는 실패 결과를 개별적으로 제공해야 한다.
- SRS-REC-008: 일괄 복구 결과는 조회·적격·적용·건너뜀·실패 수를 안정적으로 제공하고, 오류 처리 중 재점검까지 실패해도 나머지 항목 처리를 중단하지 않아야 한다. 복구 감사 callback의 실패는 복구 결과를 가리지 않아야 한다.

### 3.7 상태 확인, 관찰 및 종료

- SRS-OPS-001: 제품은 구성된 문서 정보 저장소와 문서 본문 저장소의 상태를 개별 결과로 제공해야 한다.
- SRS-OPS-002: 상태 확인 결과에는 확인 시각을 포함해야 하며, 각 대상 결과에는 대상 이름, 정상 여부, 지연 시간 및 실패 원인을 포함해야 한다.
- SRS-OPS-003: 제품은 사용 종료 시 SDK 소유 저장소 연결과 등록된 정리 자원을 안전하게 해제해야 하며, 반복 종료 호출이 오류를 일으키지 않아야 한다.
- SRS-OPS-004: 등록, 공개·관리 조회, 커서 목록 조회, 본문 조회, 삭제, 전체 데이터 삭제·적재 초기화, 상태 점검·복구 및 상태 확인은 처리 결과와 관련 문서 식별자 또는 조건을 포함한 구조화된 운영 로그를 남겨야 한다.
- SRS-OPS-005: 호출자가 제공한 저장소 연결은 제품이 소유하지 않아야 하며, 제품은 명시적으로 SDK 소유로 등록된 자원과 종료 callback에 대해서만 종료 책임을 가져야 한다.
- SRS-OPS-006: SDK는 동기 컨텍스트 관리자로 사용할 수 있어야 하며 컨텍스트 종료 시 반복 호출에 안전한 종료 동작을 수행해야 한다. 문서 본문 스트림도 동기 컨텍스트 관리자로 사용할 수 있어야 하며 정상 종료와 예외 종료 모두에서 관련 자원을 해제해야 한다.
- SRS-OPS-007: 비동기 공개 경계는 비동기 컨텍스트 관리와 비동기 종료를 지원해야 하며, 반복 종료와 취소 상황에서도 SDK가 소유한 자원을 안전하게 정리해야 한다.
- SRS-OPS-008: 제품은 등록, 공개·관리 조회, 목록, 삭제, 전체 데이터 삭제·적재 초기화, 상태 점검 및 복구의 완료와 실패 결과를 하나의 공통 작업 관찰자 계약으로 전달할 수 있어야 한다.
- SRS-OPS-009: 작업 관찰자 이벤트는 작업 종류, 성공 여부, 관련 문서 식별자 또는 목록 조건, 오류 코드, 시작·완료 시각을 포함해야 하며 문서 본문, 자격 증명, 내부 저장 위치 및 비밀 설정값을 포함하지 않아야 한다.
- SRS-OPS-010: 작업 관찰자의 실패는 원래 문서 작업의 성공 결과나 최초 실패를 변경하지 않아야 하며, 관찰 실패 자체는 구조화된 운영 로그에서 확인할 수 있어야 한다.

### 3.8 비동기 실행

- SRS-ASY-001: 제품은 문서 등록, 등록 작업 상태 조회, 공개·관리 문서 정보 조회, 문서 본문 조회, 커서 목록 조회, 논리·완전 삭제, 전체 데이터 삭제 및 데이터 적재 초기화, 상태 점검·복구, 의존 요소 상태 확인 및 종료를 포함한 모든 공개 SDK 작업에 대응하는 비동기 호출 경계를 제공해야 한다.
- SRS-ASY-002: 비동기 호출은 대응하는 동기 호출과 동일한 공식 공개 결과 모델, 입력 검증, 오류 코드, 상태 전이, 멱등성 및 부분 실패 정합성 계약을 적용해야 한다.
- SRS-ASY-003: 비동기 호출은 저장소 접근이나 동기 정리 작업으로 호스트의 이벤트 루프를 직접 차단하지 않아야 한다.
- SRS-ASY-004: 비동기 호출은 취소가 하위 동기 작업을 실제로 중단하는지 여부를 명확히 구분해야 한다. 이미 시작한 변경 작업을 안전하게 중단할 수 없으면 정합성 경계까지 완료한 뒤 취소를 전달하고, 호출자가 최종 작업 상태를 조회할 수 있어야 하며 취소를 원상 복구 완료로 표현하지 않아야 한다.
- SRS-ASY-005: 비동기 종료는 종료 작업 중 호출자 취소가 발생해도 제품이 소유한 자원의 정리를 완료해야 하며, 반복 호출에 안전해야 한다.

### 3.9 호스트 통합 경계

- SRS-INT-001: 제품은 등록, 조회, 목록, 삭제, 전체 데이터 삭제·적재 초기화 및 상태 확인 기능을 각각 표현하는 기능별 공개 계약과 이들을 결합한 전체 문서 관리 계약을 제공해야 한다.
- SRS-INT-002: 기능별 공개 계약은 공식 요청·결과·오류 모델만 사용해야 하며, 호스트의 테스트 대역이 구체 SDK 구현이나 내부 모듈을 상속·가져오기하지 않고 계약을 충족할 수 있어야 한다.
- SRS-INT-003: 제품은 호출 단위의 접근 맥락과 호스트 제공 접근 정책을 선택적으로 받을 수 있어야 한다. 접근 정책이 제공되지 않은 기존 호출은 현재와 같은 제한 없는 동작을 유지해야 한다.
- SRS-INT-004: 접근 정책은 일반 문서 정보 조회, 목록, 본문·스트림 조회, 논리·완전 삭제, 전체 데이터 삭제·적재 초기화, 내부 문서 정보 조회 및 복구 작업에 일관되게 적용되어야 하며, 일반 작업과 관리 작업의 권한을 별도로 판단할 수 있어야 한다.
- SRS-INT-005: 목록 접근 정책은 페이지를 만든 뒤 항목을 제거하는 방식으로 적용해서는 안 되며, 허용된 범위에서 커서 순서, 페이지 크기, 다음 커서 및 추가 결과 여부의 의미를 유지해야 한다.
- SRS-INT-006: 접근 맥락의 주체, 조직 및 역할 값은 호스트가 해석하는 불투명한 값이어야 하며, 제품은 특정 사용자 식별자, 조직 모델 또는 역할 이름을 고정하지 않아야 한다.
- SRS-INT-007: 제품은 작성자, 멱등성 범위, 감사 행위자 및 기본 부가 정보처럼 반복되는 값을 변경 불가능한 호출 범위 작업 맥락으로 묶을 수 있어야 한다.
- SRS-INT-008: 호출 범위 작업 맥락은 명시적인 작업별 값을 덮어쓰거나 멱등성 키를 임의 생성해서는 안 되며, 프로세스 전역 가변 상태에 저장되지 않고 동시 호출 사이에서 격리되어야 한다.
- SRS-INT-009: 특정 웹 프레임워크용 응답, 예외 처리기, 업로드 어댑터 및 생명주기 연결은 핵심 제품과 분리해야 한다. 해당 연계 계층은 기능별 공개 계약, 종료 보장 스트림, 공개 데이터 전송 모델 및 오류 설명자만으로 구현할 수 있어야 한다.

## 4. 데이터 및 상태 요구사항

- SRS-DAT-001: 문서 정보는 문서 식별자, 원본 파일명, 콘텐츠 유형, 파일 크기, 저장 위치, 상태, 생성·수정 시각을 보존해야 한다.
- SRS-DAT-002: 문서 정보는 선택적 체크섬, 삭제 시각, 작성자 및 부가 정보를 보존할 수 있어야 한다.
- SRS-DAT-003: 문서 상태는 사용 가능, 삭제 진행, 삭제 완료 및 실패 상태를 구분해야 한다.
- SRS-DAT-004: 정상 등록이 완료된 문서는 사용 가능 상태여야 한다.
- SRS-DAT-005: `UPLOADED` 상태는 과거 데이터 호환을 위한 값이며 정상 등록 흐름에서 새로 생성하지 않아야 한다. 새 문서에는 `AVAILABLE` 상태를 사용해야 한다.
- SRS-DAT-006: 공개 문서 정보는 내부 저장 위치를 제외한 문서 식별자, 원본 파일명, 콘텐츠 유형, 파일 크기, 상태, 생성·수정 시각, 선택적 체크섬·삭제 시각·작성자 및 부가 정보를 포함하는 공식 모델이어야 한다.
- SRS-DAT-007: 공개 문서 정보, 문서 페이지, 등록 결과, 삭제 결과 및 전체 데이터 삭제 결과의 canonical 직렬화는 열거 상태를 문자열 값으로, 날짜·시각을 시간대가 포함된 표준 문자열로, 중첩 부가 정보를 JSON 호환 값으로 변환해야 하며 공개 문서 정보와 그 중첩 모델에 내부 저장 위치를 포함하지 않아야 한다.
- SRS-DAT-008: 공개 문서 정보, 문서 페이지, 등록 결과, 삭제 결과 및 전체 데이터 삭제 결과는 각각 하나의 기준 공개 데이터 전송 모델과 동일한 규칙의 JSON 호환 dump를 제공해야 한다. 기존 공개 문서 정보의 호환 dump와 외부 응답용 canonical dump가 다르면 두 형식의 용도와 필드 차이를 명시해야 한다.
- SRS-DAT-009: JSON Schema를 제공하는 공식 공개 데이터 전송 모델은 실제 canonical dump의 필드명, 필수 여부, 자료형 및 중첩 구조와 일치하는 JSON Schema를 내보낼 수 있어야 한다.
- SRS-DAT-010: 내부 저장 위치는 공개 문서 정보 모델의 정의에 구조적으로 존재하지 않아야 하며, 문서 페이지나 등록 결과에 중첩된 공개 문서 정보에도 같은 규칙을 적용해야 한다. 관리·복구 전용 점검 결과는 필요한 경우 저장 위치를 포함할 수 있다.
- SRS-DAT-011: SDK 속성명과 외부 직렬화 필드명이 다르면 하나의 명시적인 serialization alias 또는 공용 dump 규칙을 제공해야 한다. 부가 정보의 SDK 속성명 `extra_metadata`는 canonical 외부 필드명 `metadata`로 직렬화하고, 기존 호환 형식은 별도로 식별해야 한다.
- SRS-DAT-012: 상태 확인, 문서 점검, 복구 계획·실행, 작업 관찰 및 업로드 작업 상태를 포함한 나머지 공식 공개 결과 모델도 JSON 호환 직렬화 규칙을 제공해야 하며, 관리·복구 결과에 포함된 내부 저장 위치는 일반 공개 결과와 혼합하지 않아야 한다.
- SRS-DAT-013: 모든 공식 공개 결과 모델의 직렬화 작업명과 날짜·시각, 열거값, 선택적 값 및 중첩값 변환 규칙은 일관되어야 하며, 같은 의미의 필드가 결과 모델마다 다른 외부 이름이나 표현을 사용하지 않아야 한다.

## 5. 비기능 요구사항

- SRS-NFR-001: 공개 API는 호출자가 입력 유효성, 접근 거부, 중복, 문서 없음, 삭제 상태, 객체 저장소 오류, 문서 정보 저장소 오류, 설정 오류, 상태 확인 실패, 멱등성 충돌·진행 상태 및 불일치를 구분할 수 있는 오류 유형을 제공해야 한다.
- SRS-NFR-002: 문서 처리와 복구는 부분 실패가 발생해도 원인과 후속 조치 판단에 필요한 상태를 보존해야 한다.
- SRS-NFR-003: 자동화된 검증은 등록, 조회, 삭제, 전체 데이터 삭제, 상태 점검, 복구, 조립 및 상태 확인의 핵심 흐름을 포함해야 한다.
- SRS-NFR-004: 실제 저장소 연동 검증은 준비된 외부 서비스를 재사용해야 하며, 외부 서비스가 준비되지 않은 환경에서는 해당 검증을 명확히 구분해야 한다. 검증을 위해 제품이 Docker Compose 또는 별도 인프라를 생성하지 않아야 한다.
- SRS-NFR-005: 사용자 안내 문서, 제품 요구사항 및 본 문서는 제품의 실제 제공 범위와 일치해야 한다.
- SRS-NFR-006: 기본 공개 등록 및 조회 결과의 문서 정보는 내부 저장 위치를 포함하지 않아야 한다.
- SRS-NFR-007: 부가 정보 스키마 검증은 외부 모델 라이브러리 의존 없이 버전 및 필드별 오류를 제공하고 기존 validator 계약을 유지해야 한다.
- SRS-NFR-008: 내보낸 복구 계획 실행은 각 작업 직전에 현재 상태를 재점검해야 하며, 복구 감사 callback 실패는 복구 결과를 가리지 않아야 한다.
- SRS-NFR-009: 모든 공개 SDK 오류는 예외 유형과 별개로 안정된 기계 판독용 오류 코드, 상위 오류 분류 및 재시도 가능 여부를 제공해야 한다. 동일한 실패 의미는 진입점이나 하위 저장소 구현과 관계없이 같은 코드와 분류를 사용해야 하며, 새 오류 코드 추가는 기존 코드의 의미를 변경하지 않아야 한다.
- SRS-NFR-010: 제품은 독립 실행형 API 서버를 제공하지 않더라도, 호스트 시스템이 공개 오류 분류를 HTTP 응답으로 변환할 때 적용할 권장 매핑을 문서화해야 한다. 이 매핑은 전송 계층 권고이며 SDK 오류 자체에 HTTP 의존성을 추가하지 않아야 한다.

### 5.1 공개 오류의 권장 HTTP 매핑

| 공개 오류 의미 | 권장 HTTP 상태 | 적용 기준 |
| --- | --- | --- |
| 접근 거부 | 403 Forbidden | 호스트 제공 접근 정책이 작업을 허용하지 않는 경우 |
| 입력값 또는 커서 유효성 오류 | 400 Bad Request | 요청 형식, 값, 크기 또는 커서가 계약을 위반한 경우 |
| 문서 또는 작업 없음 | 404 Not Found | 공개 조회 대상이 없거나 삭제 은닉 정책에 따라 없음으로 처리한 경우 |
| 중복 또는 멱등성 충돌 | 409 Conflict | 식별자 중복, 동일 키의 다른 요청 또는 현재 상태와 충돌한 경우 |
| 삭제 상태 또는 처리할 수 없는 상태 | 409 Conflict | 대상 상태가 요청 작업과 충돌한 경우 |
| 크기 제한 초과 | 413 Content Too Large | 문서 본문이 허용된 최대 크기를 초과한 경우 |
| 진행 중인 멱등성 요청 | 425 Too Early | 같은 범위와 키의 작업이 아직 완료되지 않아 재시도가 필요한 경우 |
| 설정 오류 | 500 Internal Server Error | SDK 조립 또는 호스트 통합 설정이 잘못된 경우 |
| 문서 정보 저장소 또는 문서 본문 저장소 오류 | 503 Service Unavailable | 의존 저장소가 일시적으로 요청을 처리할 수 없는 경우 |
| 상태 확인 실패 | 503 Service Unavailable | 필수 의존 요소가 준비되지 않은 경우 |
| 저장소 불일치 또는 복구가 필요한 부분 실패 | 500 Internal Server Error | 자동으로 정상 응답을 보장할 수 없고 운영 점검이 필요한 경우 |

- SRS-NFR-011: 권장 HTTP 응답 본문은 안정된 오류 코드, 상위 오류 분류, 재시도 가능 여부 및 비밀값을 제외한 진단 메시지를 포함해야 한다.
- SRS-NFR-012: 호스트 시스템은 보안 정책에 따라 진단 메시지를 축약할 수 있지만, 같은 공개 오류 의미에 대한 권장 HTTP 상태와 기준 SDK 오류 코드를 임의로 변경하지 않아야 한다. 호스트 고유 오류 코드가 필요하면 기준 SDK 오류 코드를 보존한 별도 필드로 추가해야 한다.
- SRS-NFR-013: 제품은 모든 공개 SDK 오류를 안정된 기준 오류 코드, 상위 분류, 재시도 가능 여부, 비밀값을 제외한 메시지 및 선택적 재시도 대기 시간으로 표현하는 전송 방식 중립 오류 설명자를 제공해야 한다.
- SRS-NFR-014: 권장 HTTP 변환은 전송 방식 중립 오류 설명자로부터 HTTP 상태, JSON 호환 본문 및 선택적 재시도 헤더를 생성해야 하며, HTTP 전용 값은 SDK 예외나 공통 오류 설명자에 추가하지 않아야 한다.
- SRS-NFR-015: 제품은 기본 오류 설명자를 보존하면서 호스트가 외부 메시지와 별도 호스트 오류 코드처럼 허용된 필드만 합성할 수 있는 병합 계약을 제공해야 한다. 병합은 기준 SDK 오류 코드, 상위 분류 및 재시도 가능 여부를 덮어쓰지 않아야 한다.
- SRS-NFR-016: 핵심 SDK는 특정 웹 프레임워크에 의존하지 않아야 한다. 별도 프레임워크 연계 계층은 공식 스트림, 공개 데이터 전송 모델 및 오류 설명자만 사용하여 응답 전송, 오류 변환, 등록 입력 및 생명주기를 조립할 수 있어야 한다.
- SRS-NFR-017: 자동화된 공개 계약 검증은 패키지 최상위 공개 경계에서 기능별 계약, 공통 조립 정책, 관리 자원, 파일·일반 입력 등록, 전체 목록 순회, 본문 복사, 접근 정책, 비동기 facade 및 작업 관찰자 동작을 확인해야 한다.
